# Render deployment via Blueprint with two Docker web services

We deploy to Render as two public web services defined in a root `render.yaml` Blueprint — the Spring Boot jar and the nginx-served SPA — each built from its existing Dockerfile (`backend/Dockerfile`, `frontend/Dockerfile`) with `dockerContext: .` so the frontend build can emit and the backend build can compile the TypeSpec contract. The nginx proxy no longer targets the docker-compose hostname `backend`; it proxies same-origin API calls to `${BACKEND_PROTO}://${BACKEND_HOST}`. `fromService.property: host` was rejected because it returns Render's internal hostname (e.g. `booking-calendar-backend-1fht`), which free-tier services can't resolve — nginx fails at startup with `host not found in upstream`. Instead the Blueprint hardcodes the backend's public hostname (`BACKEND_PROTO: https`, `BACKEND_HOST: <backend>.onrender.com`), which resolves publicly; the trade-off is that the literal host must be updated if the backend service is ever deleted and recreated (its `.onrender.com` suffix is random). Because Render fronts the backend behind Cloudflare, nginx needs `proxy_ssl_server_name on` so the TLS handshake carries SNI — otherwise Cloudflare rejects it (`SSL alert 40`). This keeps the SPA same-origin and avoids CORS changes. We accepted the H2 in-memory database for now — every restart or redeploy wipes bookings, slots, and schedules — and deferred Postgres (driver already on the classpath) to a follow-up, trading durability for a first deploy that stays purely operational.
